# 06. 安全の仕組みと限界、初めて動かす手順

TB-3 は、人や物に当たると壊したり怪我をさせたりする大きさと速さで動く。ここは「何が守ってくれるか」と「何が守ってくれないか」を、確かめたことと確かめていないことを分けて書く。**最後の手段は、機体の電源を切ること。**

## 1. 止まる仕組み

| 仕組み | 動き | 値（コードのとおり） | 確かめたこと |
|---|---|---|---|
| 心拍 + 見張り（`tb3-deadman`） | PC の `circle_driver` が `/tb3_pc_alive`（`Int8`）を 20 Hz で出す。機体の見張りは、これが **0.3 秒**途切れたら、車輪に 0 の `Twist` を 3 回出し、アームを「今の指令位置で止まる軌道（0.25 秒、速度 0）」に置き換える | 心拍の値のビット 1 = 車輪、2 = アーム、4 = グリッパー。0 は「PC が自分で止めた」ので見張りは外れる | **実機**: Dance 中に PC のサーバーを `kill -9` すると、最後の心拍から**約 0.58 秒**で、コントローラの指令位置が止まった（有線のとき。見張りの待ちが 0.5 秒だった最初の試験では約 0.89 秒）。**Wi-Fi 越しでの `kill -9` は試していない**。Wi-Fi 越しの心拍の間隔は、中央値 50 ms、99% が 65 ms 以下、最大 74 ms、150 ms を超えたもの 0 / 324 |
| 車輪の期限 | 機体の `diff_drive_controller` は、`/cmd_vel` が **0.5 秒**（`cmd_vel_timeout`）来ないと止まる。加速の上限は 1.0 m/s²（直進）、4.0 rad/s²（旋回）、速度の上限は 0.26 m/s・1.82 rad/s | 機体の `hardware_controller_manager.yaml` | 設定を読んだ。単独の停止試験はしていない |
| PC 側の通信切れ検知 | `circle_driver` は、機体からの `/joint_states` と `/scan` のどちらかが **1.5 秒**来ないと、Orbit・Dance・グリッパーのすべてを止める（理由 `link lost（機体との通信が途切れた）`）。**復旧しても自動では再開しない**。通信が来ていないと始められない | `STALE_S = 1.5` | **実機**: 機体の `tb3-bringup` / `tb3-watchdog` を止めて通信が途切れた状態を作ると、すべて止まり、復旧しても再開しなかった（このとき PC のドライバは試験用で、機体には何も送っていない） |
| 非常停止 | 画面の STOP ボタン、`Esc`、`Space`。画面の動きは: ① `/cmd_vel` に 0 を 3 回 ② 手先の操作・連続再生を止める ③ `POST /api/circle {"action":"stop"}`（Orbit・Dance・グリッパーを全部止める） ④ アームを、コントローラが今出している指令位置に 0.3 秒で止める（測った位置は 0.2 秒遅れているので使わない）。ゲームパッドの ○ も同じ（**ゲームパッドは未検証**） | | 画面の動作は、試験用サーバー（機体に送らない）で、アプリ内のブラウザから `estop()` を呼んで確認した（Orbit・Dance が止まる）。**実機で STOP ボタンを押して止めた記録はない** |
| 見張りの再起動 | `tb3-watchdog` は、ログに `Can't control joints` / `Can't control wheels` が出たら（モーターの電源が落ちたとき）、`tb3-bringup` を起動し直す（60 秒に 1 回まで）。OpenCR が USB でつなぎ直されたときも、udev が起動し直す | | 電池切れのあとの復帰を実機で確認（手動の再起動）。自動の再起動そのものは、電池切れから自然に戻る流れは**未検証** |

注意:

- **グリッパーは、心拍が止まっても、最後の目標の位置に留まるだけ**（切断されない）。
- OpenCR のファームウェアが、心拍（ROS 側のプラグインが 200 ms ごとに書く）が来ないときにモーターを止めるかは、**確かめていない**。
- 電池が減ると、アームと車輪を同時に動かしたときに電圧が下がって止まりやすい。電池切れで止まった直後は 11.06 V（約 32%）だった。

## 2. 走行（画面）

| 項目 | 値 |
|---|---|
| 速度の 3 段 | SLOW 0.05 m/s・0.4 rad/s、NORMAL 0.12 m/s・0.8 rad/s、FAST 0.22 m/s・1.5 rad/s（キー 1・2・3。ジョイスティックは、倒した量に比例して最大値の範囲内） |
| 押している間だけ動く | ボタン・WASD・矢印キーは、離す・タブを切り替える・ウィンドウを外す（`blur`）と止まる |
| 画面を閉じる | rosbridge が切れると、画面は 3 秒後に再接続する。切れている間の `/cmd_vel` は止まる（0.5 秒の期限） |

## 3. Orbit（円走行）

PC の `circle_driver` が `/cmd_vel` を 20 Hz で出し続ける。

| 項目 | 値 |
|---|---|
| 半径・速さ | 0.20〜0.60 m（既定 0.30）、0.03〜0.15 m/s（既定 0.10）。角速度 速さ / 半径 が 0.6 rad/s 以下 |
| 障害物の判定 | LiDAR（`/scan`）の点を機体の座標に直し、**これから通る円の帯**にある点が **3 点以上**あれば、車輪を止める（心拍と他は続く）。帯 = 円の中心から、内側が `max(0, 半径 - 0.19) m`、外側が `半径 + 0.27 m`、進行方向に **70°**（`AHEAD_DEG`、10 cm/s・半径 0.3 m で約 3.7 秒ぶん）、後ろに 6° |
| 機体自身の除外 | 機体の中心から **0.23 m** 以内の点は、機体自身（柱・電池・ケーブル）とみなして無視する |
| 再開 | 帯が **1.5 秒**空いたら、自動で再開する |
| 確認したこと | 既知の配置（正面の壁、真後ろ、円の中心の物、外側の壁、40° 先、110° 先、機体自身、右回り、ノイズ 2 点）の 11 ケースで判定が合う（`tests/test_circle_geometry.py`）。この部屋の実際の LiDAR では、左回りも右回りも、帯に点は 0 だった。試験用の設定で、指令が 20.0 Hz、角速度 0.333 rad/s（10 cm/s・半径 30 cm）になることを確認 |
| **確かめていないこと** | **実機で円を描いて走らせたことはない**。実測の角速度（IMU）が指令と合うか、半径が実際に 30 cm になるか（`/odom` は指令を積分した値で、車輪の実測ではない）は未確認 |
| 限界 | LiDAR の高さの面しか見えない（段差・低い物・高い所の物は見えない）。帯の幅の余裕は、機体の外接円の半径の推測（0.23 m）に依存する。人が近づいたときの止まる距離は測っていない |

## 4. アーム

| 項目 | 内容 |
|---|---|
| 関節の限界 | `index.html` の `LIMITS`（`q` の単位）。スライダーの範囲と `/api/check` がこれを使う。URDF の限界は `a` に対するもの（[05](05-arm-kinematics-and-mujoco.md)） |
| 動かす前の衝突判定 | 画面の Execute Pose・HOME・Orbit 前の「腕をたたむ」は、動かす前に、今の姿勢から目標までを**関節空間で直線に 24 区間**に分けて MuJoCo で判定する。当たる・限界の外なら、**動かさずに**ログに理由を出す（例: 旧 home → 「経路の 58% 地点で 関節3が限界の外」） |
| 手先の直接操作 | 100 ms ごとに、**先 0.4 秒**の姿勢を MuJoCo で判定し、当たるなら止める（答えを待たずに進めるので、判定の遅れぶん（約 0.1 秒）は進む）。机上の試験（機体には送らず）で、READY から真下へ 3 cm/s で動かすと「上段の板に当たるので止めました」と出て止まった。予測した当たる高さ（z = -6.4 cm）と合う |
| **判定が使えないとき** | サーバーの MuJoCo が読めない（`mujoco` が入っていない等）と、画面は「衝突判定サーバーが使えません。判定なしで動かします」とログに出して、**判定なしで動かす**。Dance は、MuJoCo が使えないと始められない（`POST /api/dance` が 409。メッセージは「今の姿勢からは、当たらない大きさの動きを作れません」と出て、原因がサーバーの MuJoCo だと分かりにくい）。Orbit は MuJoCo を使わない |
| 床ガード | 手先の高さの下限。画面のスライダーで -20〜+5 cm（既定 -8 cm、joint2 の軸から測る）。MuJoCo の床（joint2 軸から -17.75 cm）とは別。**板に当たる高さ（READY の位置から真下で z ≈ -6.4 cm）のほうが先に来る** |
| Dance | 始める前に、今の姿勢からの 3 秒のつなぎ込みと 24 秒の動き全体を 0.05 秒刻みで MuJoCo で判定する。関節限界（余裕 0.02 rad）と衝突（めり込み 2 mm まで許容）を調べ、**要求した大きさ**（既定 0.9）**とその 1.15 倍の両方**で当たらないことを条件に、大きさを 0.05 刻みで 0.3 まで縮める。縮められなければ始めない（409）。関節の最大速度は計画で約 0.5 rad/s、実測でコントローラの指令速度は 0.57〜0.84 rad/s |
| 実機で動かした大きさ | **0.6**（数回、15〜20 秒）。0.9（既定）は試験用の設定でしか動かしていない |
| グリッパー | 位置の範囲 -0.010〜0.019 m。Dance は 2〜8 秒周期で開閉する |

## 5. MuJoCo の判定の限界

- 車体の板の前端は写真からの推測で ±2 cm。**実物の板の前端がもっと前にあると、判定が「当たらない」でも当たる**（[05](05-arm-kinematics-and-mujoco.md) の「測ってほしいもの」）。
- ケーブル、柱（スペーサー）、電池、金具は入っていない。LiDAR は LDS-01 のメッシュ。
- 判定は 0.05〜0.1 秒間隔の標本。標本と標本のあいだ・速い動きでの隙は、1.15 倍の余裕と 2 mm の許容で見ているだけ。
- 実機の関節は指令に 0.2〜0.3 秒遅れて付き、位置のずれが平均 0.003〜0.023 rad（最大 0.06 rad）ある。

## 6. 初めて動かす手順

機体は、2026-10-26 以降、動かしていない。**必ず、機体のそばで、止められる人が見ているところで。**

1. 周りを空ける: Orbit は半径 + 40 cm（半径 30 cm なら、直径で約 1.4 m）、アームは機体の前方 50 cm 以上と、上と横。床の物（ケーブル・服）をどける。
2. **充電ケーブルを外す。** 動いたときに引っ張る。
3. 電池が十分あることを確かめる（電池切れ近くでは、動かすと電圧が下がって止まる。これまでの停止時は 11.06 V、約 32%）。
4. 機体の電源を入れて、数分待つ。`tb3ctl status` で 4 つのサービスが `active`。
5. まず**機体に指令を送らない**試験用で、画面だけ確かめる。

   ```bash
   python3 tb3ctl.py server --dry
   ```

   画面が `ONLINE` になり、LiDAR が出て、側面図が実物の腕の形と合うか。Orbit・Dance を押して、`/cmd_vel_dryrun` などに出るだけで、機体が動かないこと。止めて、本番に切り替える。

   ```bash
   python3 tb3ctl.py stop
   ```

   ```bash
   python3 tb3ctl.py server
   ```

6. STOP（画面の右上、`Esc`）の場所を確かめる。
7. 車輪: **SLOW**（キー 1）にして、前進を短く。止まること、旋回の向きが合うことを確かめる。
8. アーム: **READY**（Y）→ **HOME**（H）の順に。それぞれ、動く前に周りと、腕の通り道を見る。READY の次は、手先操作を 1 cm/s くらいで少しだけ。
9. Dance: 大きさを **0.6** にして、グリッパーも含めて、15〜20 秒。通信を止める（PC のサーバーを止める）と、約 0.6 秒で止まることを確かめてから、大きさを上げる。
10. Orbit: 半径 30 cm、SLOW 相当（10 cm/s）、左回り、**アームは折りたたんでから**（画面の `Fold arm first`）。最初は 1 周（約 19 秒）だけ見て止める。障害物（箱・足）を帯に入れて、止まって、離すと 1.5 秒後に再開することを確かめる。

## 7. やっていないこと（引き継ぐ時点）

- 実機で Orbit（円走行）を走らせたこと（指令・判定の計算と、通信が切れたときの停止は、機体に送らない試験用で確認）。
- Wi-Fi 越しで、PC を強制終了して腕が止まるまでの時間の測定。
- Dance を大きさ 0.9 で実機で動かしたこと。
- ゲームパッドの操作。
- 電池が減ったときに、Orbit や Dance が止まる・おかしくなる様子の確認。
- MuJoCo が「当たる」と言う姿勢まで、実機で実際に近づけて確かめたこと（板の前端の確認）。
- OpenCR が心拍なしで止まるかの確認。
